This is a review of the repository and its deployed dependencies, not a deployment declaration or a deletion list. **Current** describes observed source or read-only site checks; **target** is a recommendation; **candidate** means investigate before removal. ## 1. System at a glance

DungeonCrawler is a Drupal modular monolith. PHP services own game rules, campaign mutations, and content publication; the browser presents state and submits intent. The game and editors use the same Drupal application and MySQL database but have different authority boundaries. Models propose or narrate; they do not own campaign state, dice results, or publication.

```text
Author -> Editor UI / Editor GM -> revisioned command or draft service
       -> validation -> canonical library and published versions
                          |
                          v
                    campaign realization
                          |
Player -> game UI -> game coordinator -> actor/rules executors
                          |                    |
                          |                    v
                          +-------------> campaign state / log
                                               |
                       game UI <--- state, projections and narration
```

The most important seams to review are **authored versus campaign state**, **intent versus mutation**, and **stored state versus the projection seen by players**. Most proposed work closes one of those seams rather than adding another engine or another agent.

## 5. Agents, harnesses and authority

There are **three registered PHP harnesses**, not one harness per editor and not one per NPC. The [registry and its service wiring](dungeoncrawler_content.services.yml) register editor GM, runtime GM, and player automation. [Harness management](src/Service/AgentHarness/AgentHarnessManagementService.php) accounts for model execution profiles such as intent routing, runtime dialogue, tactical decision, NPC psychology, and canonical generation. A profile selects constraints for a model call; it does not give that caller write authority.

| Lane | Entry, decision and authority |
|---|---|
| Editor GM | [Editor GM harness](src/Service/EditorGm/EditorGmHarnessService.php) grounds the request on the active surface; [intent parser](src/Service/EditorGm/EditorGmIntentParser.php) and [tool registry](src/Service/EditorGm/EditorGmToolRegistry.php) expose typed functions and validate the selected tool. Tool execution is surface-scoped, and mutations go through the relevant editor or domain service. Approval and revision behavior depend on the action. [Shared chat client](js/v2/editor/EditorGmChatClient.js) is presentation, not an authority. |
| Live GM/narrator | [GM actor harness](src/Service/GmActorHarnessService.php) → [GM actor runtime](src/Service/GmActorRuntimeService.php) and [GM tool execution](src/Service/GmToolExecutionService.php). [Model invocation](src/Service/GmSubsystem/GmModelInvocationService.php) and room chat handle dialogue/narration; structured mechanics are checked downstream. Privileged GM tools bind a server-resolved actor and mutation domain; `dc_gm_mutation_audit` is the documented audit ledger. No editor publication authority. |
| Player automation | [Player agent harness](src/Service/PlayerAgentHarnessService.php) reads a scoped runtime snapshot, selects an action using policy or process flow, submits through the runtime adapter and tracks the run. It is not a replacement rules engine. |
| NPC dialogue/tactics | [NPC psychology](src/Service/NpcPsychologyService.php), encounter policy and room chat supply scoped decisions and dialogue. The [room-turn harness schema](config/schemas/room_turn_harness.schema.json) and [response projector](src/Service/GmSubsystem/ActorResponseProjector.php) shape NPC responses; the response envelope is not a fourth registered harness or a persistence guarantee. |
| Burasco / QA automation | [Python LangGraph runner](scripts/langgraph-actor-harness-run.py), [Drush adapter](src/Commands/ActorHarnessLangGraphCommands.php), and [scripted steps](config/harness/burasco-script-v1.json) drive controlled QA. It is a testing lane outside the registry, not the default harness for an ordinary actor such as Mimi. The [boundary document](docs/ACTOR_HARNESS_SECURITY_BOUNDARY.md) covers what the runner may invoke. |

**Editor surfaces:** Storyline Builder owns story content and hands the author to Dungeon or Room; it does not write their maps or delegate to another model agent. Dungeon owns site placement/links and can compose the shared room builder. Room owns geometry, ports and local objects. Definition owns catalog editing; Character Creation owns character setup; Editor Suite routes and inspects without acting as a second writer. Shared actor, definition and sheet capabilities can appear on multiple surfaces if they converge on the same write service. See the [storyline](STORYLINE_AUTHORING_PROCESS.md), [dungeon](DUNGEON_AUTHORING_PROCESS.md) and [room](ROOM_AUTHORING_PROCESS.md) flows and [surface implementations](src/Service/EditorGm/).

**Local authoring work, not the committed baseline:** District tools and Room GM bulk placement, shape and selection edits, navigation inspection, and skipped-placement gaps were present in the checkout. Their intended interaction is agent-only; the existing single-object editor controls are separate. `src/Geometry/PlacementRules.php` is a local untracked path in this snapshot. Treat district publication, gap remediation and server movement parity as open verification—not as released behavior. The [Storyline work service](src/Service/EditorGm/StorylineGmWorkService.php) is not yet a general saved-work contract for Dungeon and Room.

## 6. Gaps and recommended future state

Priorities here are for review, not approved implementation. **P1** is an authority or player-facing correctness seam; **P2** is operability/authoring; **P3** is cleanup after evidence.

| Gap | Current evidence | Target and exit check |
|---|---|---|
| **P1 · Action ownership across channels** | Coordinator/encounter is the canonical player lane; chat has separate orchestration and a mechanical mutation pipeline; direct state, dice and quest APIs have their own contracts. Old combat handlers being disabled does not prove internal executor convergence. | Build a channel → action → validator/executor → transaction/receipt matrix. Route each mutating verb to one executor behind access checks; leave presentation and explicitly non-mutating endpoints separate. Prove the same authorized operation records one outcome via UI, chat and permitted automation. |
| **P1 · Actor writes and current room** | Frozen writer register and guard show reconciliation is in flight. Actor campaign location, runtime actor room and encounter hex can represent related facts; authored location is only a starting point. | Choose and migrate one campaign room writer, define the scope of encounter-local position and consumers, and pin projections. Verify spawn, move, escort, encounter completion and reconnect; storyline republishing must not reset a live actor. |
| **P1 · Placement/playability parity** | [MovementResolverService::isPassable](src/Service/MovementResolverService.php) evaluates the hex and terrain; the map projector exposes object `blocks_movement` and local editor rules check solid occupancy. That specific method does not inspect objects; end-to-end enforcement depends on its callers. | Establish one occupancy/walkability rule for ordinary and forced movement and expose the necessary projection. Verify ports, blocked objects, movement through a gap, and an explicitly passable replacement. Keep destructible-barrier design separate until behavior is approved. |
| **P1 · Published dungeon authority** | `StorylineManagerService::validateAuthoredRoomDungeonBindings()` reads canonical dungeon row data. The editor maintains explicit versions, and compatibility must be accounted for before switching existing bindings. | Rebuild or explicitly disposition versionless attached sites, then validate/realize against the published contract. Verify a draft-only or wrong-version placement cannot satisfy a binding and that supported existing campaigns still load. |
| **P2 · Long-running authoring and model budgets** | Storyline has saved work; Dungeon and Room do not share a general resumable queue. Prompt/context growth and output truncation are distinct from tool/authority refusal. | Reuse one revision-safe work service (resume/stop/skip, bounded retries, clear results). Tag calls with surface/profile and outcome, and account separately for input budget and output truncation. Replay long drafts without letting a model summary replace saved authority. |
| **P2 · Narrative/runtime event coverage** | Narrative progression, encounter state, quest status and institutional standing meet at event boundaries; action coverage is not proven by schemas or registrations. | Record producers/consumers for actor loss/escort, quest outcome and storyline choice. Verify failure, alternative routes, reward idempotency, and visible projection after reload. |
| **P2 · Artifact and deploy observability** | Image integration, bytes, link and display are distinct. Symlinked deploys can differ from GitHub. Backup tooling was observed, but the backup/restore contract, public edge, cache/queue topology and operational alerts were not verified. | Record the served revision, dependency versions, health/readiness checks and job ownership; prove a restore covers database and media. Expose provider rejection, empty response, storage/link failures and display failures as distinguishable outcomes without logging sensitive payloads. |
| **P2 · Documentation and test entry points** | Root docs, nested docs and site-rendered architecture pages can disagree; the declared Node review script references a missing entry file. Module CI ownership and the support matrix are not demonstrated by the root manifests. | Keep this review as index, give canonical docs and checks named owners, repair or remove stale commands, and use focused contract, replay and browser checks for each changed boundary. |
| **P3 · Repo scope and retirement** | Tracked outputs, reports, HQ automation and compatibility code are mixed with live application files. | Move/archive only after checking active references, ownership, deployment and retention; remove superseded paths once replacement evidence exists. Start with low-risk tracked artifacts, not runtime adapters. |

Suggested order: establish the runtime writer/executor matrix and focused checks; close actor, navigation and publication seams; then consolidate saved work and improve deploy/media visibility. Archive candidates separately so an architecture fix does not also silently change operational tooling.
