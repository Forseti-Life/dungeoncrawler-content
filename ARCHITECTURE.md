# Architecture: DungeonCrawler Content Module

## System Overview

The DungeonCrawler Content module implements a multi-layered architecture for procedural generation and real-time gameplay:

```
┌────────────────────────────────────┐
│      UI/Presentation Layer         │
│  (Routes, Controllers, Templates)  │
├────────────────────────────────────┤
│     Game Orchestration Layer       │
│  (GameCoordinatorService, States)  │
├────────────────────────────────────┤
│      Content Generation Layer      │
│ (Generation Services, AI Providers)│
├────────────────────────────────────┤
│      Entity/Data Layer             │
│  (Campaigns, Levels, Creatures)    │
├────────────────────────────────────┤
│      Storage Layer                 │
│  (Database, Cache, External APIs)  │
└────────────────────────────────────┘
```

## Module Conversion Reader Boundary (Slice 0)

Module conversion now includes a bounded **read-only compiled-pack inspection boundary** for Foundry `packs/*` LevelDB directories. This boundary is intentionally analysis-only and has no canonical write authority.

| Field | Value |
|---|---|
| **Subsystem ID** | `module_conversion_reader` |
| **PHP contract** | `LevelDbPackReaderInterface` |
| **Default implementation** | `NodeLevelDbPackReader` |
| **Helper runtime** | Repo-owned `tools/module-conversion/read-leveldb-pack.mjs` |
| **Node package** | `classic-level` |
| **Output scope** | Structural counts, document families, rule-element/reference summaries |
| **Write authority** | None (no canonical entity/table writes) |
| **Failure contract** | Hard-fail via `ModuleConversionReadException` with structured findings |

Guardrails:
- Pack directories must resolve under approved temporary/private roots.
- Reader execution is timeout- and output-bounded.
- Skipped or truncated LevelDB values make archive inspection fail; partial inventories cannot be registered.
- Malformed embedded Adventure children (non-object rows in child collections) hard-fail inspection.
- Adventure child families outside current native mapping (for example cards/combats/macros/playlists) are still inventoried as explicit unsupported resources, not silently dropped.
- Any helper/process contract failure is surfaced as an explicit structured error.

### Module Manager Intake Surfaces (Slice 1/2)

The Module Manager is now wired as the read-only intake shell that sits above the reader boundary and archive inspector.

The adjacent `/admin/content/dungeoncrawler/module-explorer` surface lists
server-staged ZIPs in `private://module-archives`, using the same intake archive
entry validation to expose their folder structure, file bytes, and source image
dimensions to authorized Module Manager users. Download endpoints for individual
members and the original archive remain permission-checked and private; neither
preview nor download changes the conversion registry or published releases.
Source scene artwork may span multiple tactical rooms and must not be treated as
a room-sized hex-map alignment without explicit scale and shape review.

| Field | Value |
|---|---|
| **Admin route** | `/admin/content/dungeoncrawler/module-manager` |
| **Catalog API** | `GET /api/module-manager/catalog` |
| **Intake inspect API** | `POST /api/module-manager/intake/inspect` |
| **Release publish API** | `POST /api/module-manager/releases/{release_id}/publish` |
| **Primary controller** | `ModuleManagerController` |
| **Receipt ingest API** | `POST /api/module-manager/releases/{release_id}/receipts` |
| **Execution step API** | `POST /api/module-manager/releases/{release_id}/execution` |
| **Execution run API** | `POST /api/module-manager/releases/{release_id}/execution/run` |
| **Inspection service** | `ModuleConversionArchiveInspectorService` |
| **Planning service** | `ModuleConversionPlanService` |
| **Release registry** | `ModuleConversionReleaseService` (`dungeoncrawler_content_module_releases`) |
| **Plan output** | Deterministic `plan_hash` + per-resource proposal (`source` includes key/parent/collection/top_collection/document_type/embedded, then `action`, `target`, `native_commands` with typed owner/operation/command_type/payload template, `dependencies`, `losses`, `unresolved_references`, disposition) |
| **Write authority** | Intake registry only; no native content writes or publication |

Inspection endpoint contract:
- Requires a local `archive_path` inside approved intake roots.
- Accepts optional `expected_sha256` for byte-level pinning.
- Accepts optional `expected_plan_hash` to reject stale review decisions when bytes or dispositions changed.
- Returns `inventory` plus deterministic dry-run `plan`.
- Inventory includes `resource_summary` totals by type/disposition/source-collection and aggregate UUID/Compendium/module-path reference counts.
- Plan `source` metadata includes parent/key/collection/document-type/embedded flags plus per-resource structural counts and reference-count totals for object-level gap review.
- Command payload templates now include deterministic source-derived metadata scaffolding (for example room/dungeon display name and source-key description seed) while remaining non-executing preview data.
- Plan output now declares `required_receipt_resource_ids`; release receipt completeness gates consume this declared scope first, with resource-action inference as a fallback for legacy plans.
- Release mapping now tracks an execution ledger (`mapping_data.execution_ledger`) with per-resource deterministic states (`pending|in_progress|done|failed`) and summary counts. Execution updates are accepted only for plan-required `resource_id` values and only when `owner` matches one of that resource's declared `native_commands.owner` values. Receipt registration requires execution `state=done` for the resource.
- Execution-run (`/execution/run`) executes deterministic plan envelopes for selected resources. Today it executes `set_room_metadata` and `set_dungeon_metadata` envelopes end-to-end (draft command + publish) and records non-executable or failed envelopes as deterministic `failed` entries in the ledger; it never silently marks unsupported resources complete.
- Execution-run accepts `register_receipts=true`. When all required resources end in `done`, it auto-registers immutable native receipts from the execution ledger in the same request.
- Synthetic targets (`moduleconv:*`) are no longer accepted as native publication evidence. Receipt verification now hard-fails synthetic targets and unsupported receipt owners.
- Execution-run now hard-fails unsupported command types (`module_release_execution_command_unsupported`) instead of emitting synthetic success receipts.
- Native execution coverage now includes: `saveDefinition` (canonical actor/item writes validated through `CanonicalDefinitionService`), `record_reference`/`record_folder` (persisted ledger rows in `dungeoncrawler_content_registry`), and `stage_story_fact_draft` (persisted draft facts in `dungeoncrawler_content_registry`).
- `set_dungeon_metadata` execution now seeds a minimal entrance placement (published room + `is_level_entrance=true`) so converted adventure receipts can pass publication-profile dungeon validation.
- Full-module validation gate script: `tests/module_conversion_full_validation_test.php`. It fails unless **every discovered module archive** reaches `failed=0`, `succeeded=required_receipt_resource_ids count`, and `receipts_registered=true`.
- Runtime launchability gate script: `tests/module_conversion_campaign_launch_runtime_gate_test.php`. It fails unless each launchable `module_release` initializes a campaign that reaches `init.phase=structural_ready`, pins module-release provenance in profile/init context, persists runtime dungeon/room rows with authoritative room-hex H3 indices, synchronously certifies its published runtime room scope in the H3 projection ledger with matching graph-version metadata, bootstraps required campaign/dungeon/room chat sessions, and preserves connector projection parity (`dungeoncrawler_content_connections` source count equals `dc_campaign_connections` runtime count with runtime-room endpoint coherence). Launch requests only read readiness; existing campaigns missing ledger certification must be repaired through the provisioning service, not the map controller.
- Publication/catalog audit gate script: `tests/module_conversion_publication_catalog_audit_test.php`. It fails unless launch catalog entries are launchable published releases, resolve to matching native dungeon/version pins, and exclude published-but-non-launchable rows from campaign source listing.
- Campaign-create selector gate script: `tests/module_conversion_campaign_create_selector_gate_test.php`. It fails unless the `/campaigns/create` module-release selector options exactly mirror launchable published sources and stale published-but-non-launchable release IDs are rejected at form validation.
- Campaign-settings selector gate script: `tests/module_conversion_campaign_settings_selector_gate_test.php`. It fails unless `/api/campaign/{campaign_id}/settings` reports module-release options that exactly mirror launchable published sources and stale/non-launchable release IDs are rejected by the settings source endpoint.
- Scene coverage audit gate script: `tests/module_conversion_playability_audit_test.php`. It compares every scene receipt's room ID **and published version** to the pinned dungeon's placements through the release service's publication validator. It verifies that uncovered legacy releases are hidden, requires at least one fully covered launchable release, and does not mistake a generated entry room for source coverage; this is necessary but not sufficient for playability.
- Gate suite runner: `bash tools/module-conversion/run-gates.sh` executes all module-conversion release gates in one command (negative contract checks, full validation, runtime launchability, publication catalog audit, create-selector parity, settings-selector parity, playability audit). Its playability audit requires an attested, launchable scene-covered release; the historical entry-only releases do not qualify.
- Intake now enriches each resource with `source_context` (typed source details such as scene grid/dimensions, background and indexed tile placements, actor/item type hints, journal text lengths, and rolltable formulas) plus `missing_source_fields` (required fields still absent). Planner propagates both into `plan.resources[].source` for conversion functions to fill gaps from module context.
- Accepts optional `decisions.resource_dispositions[resource_id]` review overrides (`reference_only | requires_authoring | unsupported`); decisions cannot assert native conversion.
- `register_release=true` requires both `expected_sha256` and `expected_plan_hash`, then stores an intake identity keyed by module id/version and archive hash, always `requires_authoring`.
- Release registration now also enforces a deterministic plan contract (`schema_version`, per-resource source metadata, and typed command proposal metadata) so stale/forged preview payloads are rejected before intake persistence.
- Native conversion receipts can now be registered as immutable per-resource records in release `mapping_data.native_receipts`; conflicting receipt rewrites are rejected. Complete receipt coverage advances status to `receipts_recorded`, but campaign launch remains disabled until full native publication/verification wiring is implemented.
- A release can now move to `published` only through a verified launch manifest (`dungeon_id`, `version_id`, `receipt_resource_id`) that must match a recorded `DungeonEditorService` receipt and an actually published canonical dungeon/version pin in native stores. Registration also reads the pinned dungeon payload and requires exactly one placement of **every** converted scene receipt (room ID and version). Each scene receipt must match its source resource, carry the explicit `playable_validated` state, and contain at least one object placement; once scene coverage is complete, the pinned dungeon must pass the canonical publication validator (including reachability and port links). It records a scene-coverage attestation tied to the pin; missing attestations and zero-scene releases are not launchable.
- `listPublishedCampaignSources()` / `resolveCampaignSource()` now expose only launchable published releases whose manifest and native pins still verify; stale, drifted (for example dungeon later unpublished), or otherwise unverified rows are filtered/rejected at read time.
- Release rows now include a computed `launchable` flag derived from the same read-time verification (status, receipt completeness, manifest integrity, and native dungeon/version pin checks).
- Campaign creation now revalidates selected `module_release` launchability at form-validate time so stale selections are blocked before initialization.
- Campaign create/settings module-release selectors display published but unlaunchable releases as "published, not playable: maps and routes not converted"; settings disables those options, and both write paths still reject their IDs through `resolveCampaignSource()`. Only releases returned by `listPublishedCampaignSources()` can launch. The two real releases have 10–11 receipt rooms but no placed scenes; each scene room has the editor's default 19 hexes and one default entry port, with zero exit ports and zero object placements. Simply placing receipt rooms would not make them playable.
- Campaign create/settings published-dungeon selectors collapse same-titled editor identities to the newest published copy (by publication time, with a deterministic tie-break); stale dungeon IDs are rejected when saving or launching.
- Launchable published releases are treated as immutable intake identities; later `registerRelease()` calls are rejected and changes must use a new module version.
- Receipt ingest API validates CSRF + non-empty receipt list and writes through `ModuleConversionReleaseService`; it cannot set `published` or expose launchable sources.
- Hard failures remain explicit via structured findings; there is no fallback success payload.

**Playable-adventure remediation plan (original survey published; tactical/source-fidelity signoff outstanding):**

**Island 1.1.0 diagnostic/acceptance case (read-only local archive audit):** The Adventure pack embeds 10 scenes, 17 actors, 119 actor-held items, 3 journals with 8 nonempty pages (roughly 10 KB of text), 55 tables, and additional resources. All 10 scenes have actual dimensions, grid settings, navigation order, and background references; collectively they have 9 tiles (five distinct tile images) and 12 drawings, but zero scene tokens, walls, notes, or scene-to-journal references. Their 10 background and 9 tile image references resolve to files in the archive; all nine tile occurrences also carry explicit source x/y/width/height, now preserved as indexed placement evidence, but no asset has been imported into Dungeoncrawler. This is a *partially authored source*, not an empty archive. Before this slice, the LevelDB summary dropped scene dimensions/grid/background, tiles/drawings, tile-image references, and page-text lengths; the inspector supplied synthetic 600x600 square defaults and reported no missing scene fields. The reader now retains those source facts, rejects malformed present scene fields, and the inspector records missing fields before any normalization; newly created room receipts preserve scene geometry and background/tile references in metadata marked `source_metadata_only`. The scene coverage gate rejects even placed rooms still carrying that state. Existing published releases remain unchanged. The room itself still has the editor's default 19 stone hexes, one entry port, zero exits, and zero placements; these receipts are structurally valid, **not playable map conversions**. Do not commit third-party module assets/text as fixtures; make project-authored fixtures with analogous structure and test real archives read-only.

**Required conversion/enrichment flow:** Preserve raw-source *presence* separately from normalized defaults and record per-field provenance. Convert supported scene geometry/objects and authorized assets deterministically; classify truly absent gameplay semantics (tokens, walls, encounters, exits, transitions, quest/objectives) as explicit enrichment requirements rather than success receipts. Feed permitted structural/contextual signals into the *existing* `CanonicalGenerationService` via `EditorCanonicalGenerationPlanService` and the canonical Room/Dungeon Editor command path to generate original Dungeoncrawler-specific replacements. The shared dungeon layout planner accepts `required_room_ids` and module conversion now uses it to place each selected scene room exactly once. Simulate and validate the resulting room commands, placed definitions, port graph, entrance, interactions, and quest/runtime projection before making the immutable conversion revision playable. A missing provider, invalid source contract, unvalidated generated result, or unresolved required content must fail closed; enrichment for genuinely absent optional source content is not a recovery fallback for errors. Island passes only when all 10 scenes have source-backed or validated generated playable rooms in a traversable dungeon and required narrative/interaction coverage, not when metadata receipts alone complete.

**Asset boundary:** Source dimensions/grid/distance and background/overlay references are *evidence*, not a direct mapping to hex coordinates or a playable terrain texture. Island's upstream `1.1.0` tag publishes an MIT `LICENSE` and its README attributes text/maps to Tom McCafferty; it separately identifies third-party portrait/token sources. Author-created maps may be reused with the MIT copyright and permission notice retained, but portraits/tokens need separate authorization and must not be treated as MIT merely because the repository has a license. The downloaded module ZIP omits the license file, so include the upstream tagged notice when distributing any authorized map copies. The inspector resolves background and ordered tile paths against archive files, including URL-encoded names; map staging is wired into the original-generation runner and persists images and adjacent MIT notices in the existing image repository. Exact pinned rooms retain archive entries and staged public links for gallery and gameplay visual projection; the canvas draws art only with explicit reviewed alignment. `ModuleSceneGenerationAdapter` builds original canonical rooms from structural geometry and project-original definition references, validates reachable ports and placed objects using canonical movement authority, and supports an explicit terminal room without a dangling exit. These structurally valid drafts do not infer source walls or terrain from image pixels.

**Reviewed opt-in execution:** `ModuleConversionReleaseService::executePlannedCommands()` accepts `original_scene_generation` only on the existing execution endpoint: `{ "scene_definitions": { "<scene resource_id>": { "metadata": { "name": "...", "description": "...", "theme": "...", "rights_status": "project_original" }, "definitions": [ { "family": "item", "definition_id": "...", "version": "1.0.0", "rights_status": "project_original" } ], "maps": { "background": "<per-image attestation>", "tiles": [] } } }, "terminal_scene_resource_id": "<scene resource_id>", "dungeon": { "name": "...", "description": "...", "theme": "...", "rights_status": "project_original" }, "seed": 7 }`. Require exactly all plan scenes (3–16) and one adventure, optionally matching `resource_ids`, one terminal, a positive author UID and plain semantic `publish_version`; all scenes execute in plan order before assembly from same-run room/version receipts. Reviewed display text and definition refs never reach the generation provider; structural geometry does. Room/dungeon publication-profile validation is mandatory; adapter failures roll back the scene batch and discard staged art. Calls omitting opt-in retain the metadata-only path. Without explicit map-role and quest review, generated receipts say `original_gameplay_generated_map_staged` if maps are attested (or `..._unattached` otherwise), **not** `playable_validated`; scene coverage and both generic launch boundaries reject them even when the dungeon is connected and published. The reviewed **interpretive survey** path below may publish original canonical terrain and gameplay with gallery-only source art; it does not certify tactical-map alignment.

An optional `maps` field on **every** `scene_definitions` entry contains `{ "background": <per-image attestation>, "tiles": [<attestation in tile order>, ...] }`; partial batches are rejected. The stored release archive and inspected inventory pin each image, and the existing image repository stores the original bytes plus their notice files. The resulting source-scene metadata includes ordered tile placements and public image/notice links. These rooms and their assembled dungeon say `original_gameplay_generated_map_staged` / `map_attachment_state: staged`, **not** `playable_validated`; both the module release gate and generic dungeon launch still reject them. The room-view gallery displays source art separately from canonical hex terrain. `registerRelease()` accepts an independent `release.conversion_revision` (default `base`) to create a new immutable conversion against identical source bytes.

### NPC Motivation → Tactical Intent Contract (Encounter autoplayer)

Authoritative server implementation lives in:
- `src/Service/EncounterPhaseHandler.php`
  - `buildNpcTacticalIntentContract(...)`
  - `buildNpcTurnPlan(...)`
  - `resolveNpcIntentActionType(...)`

Contract shape:
- `intent`: canonical behavior mode (`deescalate`, `self_preserve`, `finish_weakest`, `treasure_seek`, `aggressive_engage`, `no_targets`)
- `action_sequence`: deterministic per-action sequence used for remaining turn actions
- `target_strategy`: deterministic targeting mode (`nearest`, `weakest_adjacent`, `none`)
- `decision_reason`: concise machine-readable reason for the selected intent
- `decision_basis`: supporting tactical/psychology evidence (attitude, axes, hp ratio, goals, adjacency/target state)

Execution guarantees:
- NPC turns use one intent contract for action 1/2/3 so behavior does not drift mid-turn.
- Encounter outputs expose `decision_reason` and `decision_basis` on `npc_strike`, `npc_stride`, `npc_interact`, `npc_talk`, and `npc_choose_not_to_act`.
- AI recommendation prompts include `current_actor_tactical_intent`; optional AI first-step seeds are accepted only when compatible with the same server intent contract.

## Known Limitations

1. API generation subject to LLM rate limits
2. Real-time features require persistent WebSocket (use with caution)
3. Large party sizes (>6) may impact performance
4. Historical state replays limited to current session
5. Procedural content may rarely violate PF2E rules (manual review recommended)
